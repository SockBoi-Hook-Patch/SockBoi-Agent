# v0.4 — Controlled Active Assessment Design

## Goal

Move SockBoi Agent from planning-only toward executing narrowly scoped security checks against assets covered by an explicitly authorized engagement. This milestone does not enable unrestricted exploitation or arbitrary command execution.

## Execution contract

Every executable assessment action must be represented by an immutable action envelope containing:

- engagement ID and tenant ID;
- canonical target and protocol;
- adapter/tool ID and exact technique ID;
- normalized parameter digest;
- risk classification and requested time window;
- approval ID and authenticated requester/reviewer identities.

The policy layer must recompute and validate this envelope at execution time. A prior approval is invalid if any bound field differs, the engagement is closed, the approval is expired/revoked, or the actor lacks permission. Approval is single-use for active checks.

## Required controls before enabling execution

1. **Identity and authorization**
   - Authenticate every non-health API request.
   - Derive actor identity from verified credentials; never accept actor identity from request bodies or query parameters.
   - Enforce role permissions and tenant isolation in the data-access layer.
   - Deny by default when identity or tenant context is missing.

2. **Engagement scope**
   - Normalize hostnames, URLs, IP addresses, and CIDRs before comparison.
   - Resolve DNS and validate every resolved address immediately before connecting.
   - Reject redirects by default; if a redirect feature is later added, revalidate every hop against scope.
   - Prevent DNS rebinding and cross-scope redirects.

3. **Adapter isolation**
   - No arbitrary shell, Python, or user-supplied command execution.
   - Each adapter exposes a fixed typed schema and a fixed set of techniques.
   - Run adapters in a restricted worker with CPU, memory, wall-clock, concurrency, and network-egress limits.
   - Apply per-engagement rate limits, cancellation, and bounded response sizes.

4. **Approval and audit**
   - Approval binds the complete action envelope, not merely a target and technique label.
   - Require a distinct authenticated reviewer for active actions.
   - Record immutable, append-only events for request, decision, dispatch, completion, timeout, and denial.
   - Never treat agent/LLM output or imported Skills as authorization.

## Initial adapter profile

The first live adapter should be a deliberately narrow HTTP security-configuration inspection profile:

- HTTP GET only; no form submission, state-changing methods, authentication bypass, exploit payloads, or credential collection.
- Inspect response security headers and TLS configuration.
- Disable redirects and ambient proxy configuration unless explicitly configured by the operator.
- Restrict destination ports and response size.
- Use strict connection/read timeouts and low request rates.
- Require an active-check approval bound to the exact URL, adapter, technique, and parameter digest.
- Store only bounded evidence and redact secrets before persistence.

A separate isolated-lab profile may later add more intrusive verification techniques, but it must not weaken the production policy gate.

## Acceptance criteria

- Unauthenticated requests cannot create engagements, request/decide approvals, read findings, or dispatch work.
- A user cannot access another tenant's engagements, approvals, findings, or audit events.
- Changing one byte of a previously approved action envelope causes execution denial.
- Expired, revoked, reused, cross-engagement, or self-approved approvals are rejected.
- Out-of-scope DNS answers, redirects, IPs, and ports are rejected before network connection.
- Adapter tests use mock transports by default; live integration tests run only against an explicitly configured local test fixture.
- CI covers positive and negative policy paths, and no live target is contacted during ordinary unit tests.

## Release gate

Active execution remains disabled until identity, tenant isolation, action-bound approval, durable storage, audit integrity, and adapter isolation have all passed tests and review. The API must not expose a generic execute endpoint.
